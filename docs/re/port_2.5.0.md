# Address port 2.3.1 -> 2.5.0

Generated by `scripts/port_addresses.py` from A6656ADCFBE236A49B9DB4A9DE645089 to 7D7382D0EADD36F0BA1CCEBEC1D5BEBC. Every entry verified on the old build is listed with the evidence that ported it (see the script's docstring for what each kind requires); NOT PORTED entries lost `verified`.

{'ported': 113, 'not ported': 477}. Ten more were added by hand and ISerializable_sub_C0 moved to a new hash (see Manual entries).

## Manual entries

The matcher found no evidence for these four, so each was located by hand in the 2.5.0 binary. In 2.3.1 the CBaseFunction base constructor was inlined into every derived ctor. In 2.5.0 it is out of line, so each derived ctor is now a small wrapper around it.

**Base ctor `0x101097DE8`**, entered through the thunk `b` at `0x101097EEC`. It runs `mov x20,x3; mov x19,x0`, then:

- stores the CBaseFunction vptr `0x10782FE80` at +0;
- stores `x1` and `x2` (fullName, shortName) at +8 and +0x10;
- zeroes +0x18 and +0x20;
- initializes the DynArrays.

This is the same as the inlined body in 2.3.1 `0x1021739E8`, which stored vptr `0x106FFAC48`.

Its callers are the CBaseFunction-derived ctors. Each comes as a pair of identical copies. One copy of each pair has no callers, and the game calls the other. The entries below are the copies the game calls.

The fourth caller of the base ctor, `0x10109BB60`, was rejected. It stores vptr `0x10782FF30`, puts `x1` at +0xF0 and registers no native function, so it is CScriptedFunction.

The derived fields moved from +0xB0 to +0xF0 because CBaseFunction grew from 0xB0 to 0xF0. Upstream RED4ext.SDK records this growth in 0f5eba42 ("Add support for patch 2.5"), and the SDK headers here must carry it too.

**CRTTISystem_Get `0x1010B3CAC`** is a function-local static singleton getter:

- It checks the guard flag at `0x108055E78` with `ldaprb` and returns the object at flag+0x20, `0x108055E98`.
- 2.3.1 `0x102188E8C` has the same shape, with flag `0x107D6A268` and object `0x107D6A288`.
- It is the tail-call target of the thunk `0x1010B3288`. The matcher mapped that thunk to 2.3.1 `0x1021885A0` with 229 call votes, and the two thunks make the same virtual calls at slots +0x38 and +0x80.
- It is in LC_FUNCTION_STARTS.

**CStackFrame_dtor `0x1011AB310`**, hash 2502822355 (`0x952E09D3`). This hash is new in upstream 0f5eba42.

ExecuteScripted `0x101098FC0` is the tail-call target of the thin wrapper `0x10109B220`. The matcher mapped that wrapper to 2.3.1 `0x102173390` with 37 votes. ExecuteScripted builds its frame at `sp+0x68` with the frame ctor `0x1011AB150` (entered through thunk `0x1011AB268`) and ends with `add x0, x19, #0x68; bl 0x1011AB310`.

The ctor matches upstream's 0xA8 CStackFrame layout:

- isRoot at +0x64;
- the call map at +0x68, cleared with `0xFFFFFFFF` at +0x88;
- the allocator at +0x90;
- `+0x98` = &+0x68 for a root frame, otherwise the parent's +0x98;
- `+0xA0 = 0`.

The dtor clears the map at +0x68/+0x70/+0x74/+0x78 and frees it through the allocator object at +0x90 (vt+0x20 with `x0 = frame+0x90`). Its twin copy `0x1011AB26C` has no callers.

The allocator object is a bare vptr. The game builds it with `0x104E33920`, which stores vtable `0x107CDDB78`: slot +0x20 is Free and +0x30 is GetHandle. The SDK's `Memory_PoolScript_vtbl` relocation is not used on macOS. The frame ctor copies the vptr of the SDK's own `Allocator<PoolScript>` instead, which forwards to the game's exported `PoolStorageProxy<PoolScript>`.

**ISerializable_sub_C0**: upstream 0f5eba42 renamed the hash from 2149588021 (`0x80201C35`) to 3689484881 (`0xDBE91251`) because the Windows pattern changed. It is the same function, so the ported, verified 2.5.0 address `1:0x10B0B44` moves to the new hash. The old hash is dropped because the SDK no longer references it.

**DefaultFixedCallbackBufferSize 64** (also from upstream 0f5eba42) holds on macOS too. The 2.5.0 exports no longer include `FixedSizeFunction<..., 32, 8>` (2.3.1 had 228), and `<..., 64, 8>` went from 25 to 253.

**CBaseFunction_ExecuteScripted `0x101098FC0`**, hash 3791200470.

- The thin wrapper `0x10109B220` tail-calls it. The matcher mapped that wrapper to 2.3.1 `0x102173390` with 37 votes; 2.3.1's wrapper did `bl 0x102172BF4` (the old ExecuteScripted), then returned 1.
- The body matches the old one: alloca of `func->unkAC` bytes of locals, then `stack->vt[+0x28]` fills them, then the frame is built (see CStackFrame_dtor above) and the bytecode runs.
- It returns a bool in w22 (0 or 1), so the SDK's `bool(CBaseFunction*, CStack*, void*)` holds.
- The four tail-callers `0x10109B168/B220/B27C/B310` stand in for 2.3.1's four BL callers.

**CBaseFunction_InternalExecute `0x101099FBC`**, hash 404169501.

- Prologue: `stp x28,x27,[sp,#-0x60]!`.
- It keeps the same five arguments (x0 to x4), tests the isNative bit with `ldrb w8,[x0,#0xa8]; tbnz w8,#0`, and reads `[x0+0xAC]` for the locals alloca. It then calls the param setup `0x101098C5C`, which the matcher mapped (callee set) to 2.3.1 `0x102172880`.
- That is the 2.3.1 `0x102173120` sequence instruction for instruction.
- Like the old function, it has exactly two callers: `0x101200F5C` and `0x101201260`.

**Data entries with a single vote.** The porter needs two votes for data (see the docstring), so these three were checked by hand.

- **CStack_vtbl `0x1078300D8`** (2:0xD80D8). Old `0x106FFAEA0` had slots 0, 2, 3, 4, 5 and 6 pointing at functions the matcher mapped.
